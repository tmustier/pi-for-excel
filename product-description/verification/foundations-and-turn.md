# Verification: foundations and turn

How to run this file: bring up Pi in Excel on the web with `node scripts/orb/excel-web-session.mjs --check` (see [docs/orb-excel-web.md](../../docs/orb-excel-web.md)), or use Excel desktop where the Device column says so. Seed Sheet1 with a small table (A1:D10: \"Region\", \"Q1\", \"Q2\", \"Total\", eight regions with numbers, `=B+C` totals in D2:D9 and a total row whose D10 shows `#VALUE!`). Start each section from one tab with an answered conversation, execution mode Auto, a reasoning model, and the default thinking level. Every item that needs Pi \"responding\" uses a real model turn; keep them small: \"Without using tools, write the numbers one to three hundred as English words, one per line.\" keeps a tab responding for 10–20 seconds; \"Call read_range three times in parallel in one response, for A1:B3, C1:D3 and A4:D6. Then reply with just DONE.\" gives a tool batch; \"Use execute_office_js to run code that only waits 12 seconds … Then reply with just DONE.\" holds a tool running. Steers and follow-ups use \"Then say BANANA.\" and \"Then say MANGO.\" so their delivery is easy to spot.

- `web` — Excel on the web, with key presses and mouse events delivered to the taskpane through the DevTools protocol (real, trusted events; Pi's capture-phase shortcuts and Office.js both see them).
- `web-grid` — as `web`, plus typing into the Excel grid itself (key events sent to the Excel page, not the taskpane).
- `web-inject` — as `web`, with a provider failure simulated from the taskpane's console: the active tab's agent `streamFunction` is wrapped so its next call waits a few seconds and then throws. Everything after the throw is the product's own handling.
- `web-observe` — as `web`, reading something the product does not show (the note auto-context sends) by wrapping the active tab's context transform from the console. Observation only; the request is unchanged.
- `web-slow` — as `web`, with `Excel.run` in the taskpane wrapped to wait 8 s before each call, so a write holds the workbook lock long enough to act on.
- `desktop` — Excel desktop on Windows or macOS.

Some `web` items need a condition the orb cannot produce for real; the Setup cell names it, and everything after it is the product's own handling. The model's context window is shrunk in memory (`agent.state.model.contextWindow = N` on the registry object, so the periodic model refresh keeps it) to trip the meter colours and auto-compaction with ~20k tokens. The tab's model is switched in memory to an Anthropic model to get a provider with no credential. The orb's own `proxy` service is stopped and restarted (`amp orb service stop proxy`, `amp orb services ensure`) for the proxy banner and network loss. A 429 is returned for one request by CDP `Fetch` interception. A file drop is delivered with CDP `Input.dispatchDragEvent`. Reloads use `location.reload()` in the taskpane frame (CDP `Page.reload` only works on top-level targets).

Results below are from a first pass in Excel on the web on 2026-10-26, run by an agent driving the orb's Excel Chrome over CDP (port 9223), against pi-for-excel commit `ec453df`, with the model GPT-6.1 Sol through a ChatGPT (openai-codex) login, 500k context window. The pass recorded the taskpane's state on every DOM change (send/Stop button, working indicator, queue strip, banner, toast, placeholder, tool cards and groups, thinking labels, transcript follow state, busy dots), read the agent's state (messages, steer and follow-up queues) and took screenshots of the taskpane. It did not judge timing by eye beyond those recorded timestamps, did not use a screen reader, did not run Excel desktop, did not drop real files from the desktop and did not exhaust a real context window. A second session the same evening (after a usage-limit pause) built a ~50k-token history from two 1,250-row reads to exercise `/compact`, simulated a context overflow with `web-inject`, and held the workbook lock by delaying every `Excel.run` in the taskpane by 8 s (`web-slow`). A third session ran every remaining web item with the techniques above. Totals: 147 items, 133 pass, 10 fail, 4 blocked (needs desktop), none not run. `blocked (needs desktop)` items are for a desktop pass. A `pass (bug confirmed)` means the document states a suspected bug and the product does what the document says.
